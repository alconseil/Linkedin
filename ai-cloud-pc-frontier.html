01

Un changement de paradigme silencieux

Depuis mai 2024, Microsoft a progressivement déployé sa gamme Copilot+ PC — des machines physiques équipées d'un NPU spécialisé capable d'exécuter des inférences IA localement, à plus de 40 TOPS (Trillion Operations Per Second). La promesse : Recall, Click to Do, recherche sémantique, Live Captions avec traduction en temps réel, tout ça off-cloud, rapide et privé.

Le problème ? Ces expériences étaient réservées aux seuls appareils physiques certifiés Copilot+. Un parc de 10 000 PC non éligibles, une flotte VDI ou un utilisateur sur Mac ? Aucun accès.

💡 Le shift Les Windows 365 AI-enabled Cloud PCs inversent la logique : c'est désormais Azure qui joue le rôle du NPU. La puissance de calcul IA est mutualisée dans le cloud Microsoft, et l'utilisateur reçoit une expérience Copilot+ streamée sur n'importe quel terminal — même un vieux PC x86, un iPad ou un Chromebook.

Ce service est déployé dans le cadre du Microsoft Frontier Program, une initiative d'accès anticipé qui n'est pas un simple programme bêta, mais un programme de co-création où les participants influencent directement la roadmap produit.

02

Copilot+ PC physique : le seuil des 40 TOPS

Pour comprendre ce que démocratise le Cloud PC AI-enabled, il faut saisir la contrainte matérielle qu'il contourne. Un NPU (Neural Processing Unit) est une puce dédiée à l'inférence d'IA, optimisée pour les opérations matricielles en faible précision (INT8, FP16) — là où un CPU ou GPU généraliste consomme bien plus d'énergie pour le même résultat.

⚠️ Attention au marketing Certains constructeurs affichent "90 TOPS" ou "120 TOPS" en additionnant CPU + GPU + NPU. Seul le score NPU isolé compte pour la certification Copilot+. Un NPU à 13 TOPS avec un GPU à 77 TOPS = non éligible, même si la somme dépasse 40.

Fonctionnalités disponibles (Frontier Preview)

🔍 Improved Windows Search (Recherche sémantique)

La recherche Windows traditionnelle s'appuie sur les métadonnées de fichiers (nom, date, extension). La recherche IA interprète l'intention de l'utilisateur en langage naturel et indexe le contenu des documents.

Exemple concret Un fichier photo nommé IMG_2841.jpg représentant une voiture rouge. Recherche classique "voiture" → 0 résultat. Recherche sémantique → le fichier apparaît. La recherche couvre les fichiers locaux et OneDrive simultanément, avec une interface unifiée dans la barre des tâches et l'Explorateur de fichiers.

Langues supportées : Français, Anglais, Allemand, Espagnol, Japonais, Chinois simplifié.

En test comparatif sur OneDrive : la recherche IA a retourné 37 résultats versus 10 pour la recherche classique sur le même corpus — soit une amélioration de +270 % de rappel.

Click to Do contextualise les actions disponibles sur n'importe quel élément visible à l'écran — texte sélectionné, image, zone d'une page web. On l'active via Windows + Q ou en maintenant la touche Windows + clic gauche.

Sur une image : Recherche visuelle, Extraire le texte, Décrire l'image, Actions contextuelle M365 Copilot.

Quel impact pour les grandes entreprises ?

Dans les contextes enterprise que je gère (flottes > 10 000 endpoints, architectures VDI, Intune @ scale), voici les angles qui me semblent les plus pertinents :

📊 Cas d'usage immédiat Pour les organisations ayant déjà déployé Windows 365 Enterprise avec des SKUs ≥ 8vCPU/32GB — comme des postes analytiques, des profils développeurs ou des VDI lourd — l'activation ne coûte qu'un toggle Intune. Pas de budget supplémentaire, pas de migration. C'est le POC le plus rapide de 2026.
⚠️ Points de vigilance 1. SKU sizing : Les SKUs 2vCPU/4GB ou 4vCPU/8GB ne sont pas éligibles. Vérifier votre catalogue Windows 365 avant d'annoncer la disponibilité aux métiers.
2. Région Azure : Confirmer que vos Cloud PCs sont provisionnés dans une région supportée. Germany West Central est maintenant disponible — bonne nouvelle pour la conformité RGPD des entreprises allemandes ou opérant sous droit allemand.
3. Diagnostic data : Activer l'envoi de données de diagnostic optionnelles (requis pour l'indexation sémantique). À documenter dans votre DPIA si vous êtes soumis au RGPD.
4. Recall absent : La feature de "mémoire" des sessions n'est pas disponible sur Cloud PC — l'inférence locale remain requise pour cette workload.

Ces points sont valables pour les Cloud PCs humains. Mais la convergence avec Windows 365 for Agents introduit une dimension supplémentaire à anticiper dès maintenant.

Windows 365 for Agents : le piège des identités agentiques dans Intune

Windows 365 for Agents permet à des CUA (Computer Use Agents) créés avec Copilot Studio de s'exécuter sur des Cloud PCs sécurisés, Entra-joinés et Intune-enrollés. L'objectif : des agents IA autonomes capables d'ouvrir des apps, traiter des données et automatiser des workflows — sans infrastructure dédiée.

Mais lorsqu'on mélange Cloud PCs humains et Cloud PCs agentiques dans le même tenant, une subtilité d'implémentation peut bloquer vos politiques Intune.

Les 3 objets Entra créés par chaque agent Copilot Studio

Objet EntraTypeRôleVisible dans Intune ?
Agent blueprint App Registration Template de l'agent — définit permissions, scopes Graph, config auth Non
Agentic app instance Service Principal Identité runtime pour l'authentification — credentials fédérés Teams ⚠ Oui — comme SP
Agentic user User (idtyp=user) Identité visible dans l'org — peut avoir mailbox, OneDrive, licence M365 Partiel
⚠️ Le problème concret Quand Intune cherche à cibler un agent, il rencontre l'agentic app instance — un Service Principal. Or Intune gère ses politiques de provisioning via des groupes d'utilisateurs ou de devices, pas via des Service Principals. Le ciblage ne s'applique pas correctement si la membership est gérée directement depuis Intune.

La recommandation : gérer dans Entra, cibler depuis Intune

Architecture de gestion recommandée
# Flux recommandé ─────────────────────────────────────────────

Copilot Studio  →  crée  →  Agentic User (idtyp=user)
                              ↓
                    Entra ID  →  groupe  →  "All Agentic Users"
                              ou groupe de sécurité dédié
                              ↓
                    Intune  →  cible ce groupe  →  politiques W365 for Agents

# À ÉVITER ────────────────────────────────────────────────────
# Gérer la membership directement dans Intune
# → Intune voit le Service Principal, pas l'Agentic User
# → Les politiques de provisioning Cloud PC ne s'appliquent pas

# Vérification : l'agentic user a bien idtyp=user dans son token
# Pas de credentials traditionnels (password, passkey, MFA factors)
# Exempt des politiques MFA — à prévoir dans les CA policies
Agentic User — caractéristiques
  • ✓Token avec idtyp=user — se comporte comme un user
  • ✓Peut être ajouté au groupe "All Agentic Users"
  • ✓Assignable à une licence M365 E5, Teams, Copilot
  • ✓Visible dans l'organigramme et les People Cards
  • ⚠Aucun credential traditionnel — MFA exempt
  • ⚠Lié de façon immuable à son agentic app instance
Intune — état actuel (preview)
  • ✓Cloud PCs agentiques visibles : Devices → Windows 365 (filtre partner)
  • ✓Entra-joinés et Intune-enrollés comme les Cloud PCs humains
  • ⚠Identités agentiques affichées comme Service Principals
  • ⚠Membership de groupe à gérer depuis Entra, pas Intune
  • ⚠Pas d'assignation directe de politiques via l'identité agentique
✅ Bonne pratique opérationnelle Créer des groupes de sécurité Entra dédiés par type d'agent (ex. GRP-W365-Agents-CopilotStudio, GRP-W365-Agents-ProjectOpal) en y ajoutant les agentic users (pas les service principals). Cibler ces groupes depuis Intune pour appliquer les politiques Windows 365 for Agents. Cette séparation humain/agentique est critique dès que votre tenant héberge les deux types de Cloud PCs simultanément.

A quiet paradigm shift

Data processing
  • ✓Ephemeral processing via secure Windows 365 cloud service
  • ✓No personal data stored in the AI cloud service
  • ✓Data is never used to train AI models
  • ✓Semantic index stored in the Cloud PC only

  • ✓Data stored in the Azure region of the provisioned Cloud PC
  • ✓EUDB (European Data Boundary) supported

  • ✓AI features disabled by default — explicit opt-in
  • ✓Enable per Entra ID group (user-level granularity)

  • ⚠Disable policy takes precedence over Enable in conflict
Retention & Audit
  • ✓User data retained max 90 days post-deletion
  • ✓Audit, export, deletion via standard Microsoft Intune
  • ✓Defender for Endpoint alerts: 180 days
  • ⚠Optional diagnostic data required (Windows Privacy Settings)
✅ Bottom line for CISOs & DPOs AI inference data never leaves your Azure perimeter. The semantic index stays inside the Cloud PC. No data is used for model retraining. The service complies with EUDB and GDPR — a major differentiator versus third-party AI tools that pool data across tenants.

Enterprise impact: what you need to act on now

From my experience managing large enterprise fleets (10,000+ endpoints, VDI architectures, Intune at scale), here are the angles that matter most:

📊 Immediate use case Organizations already running Windows 365 Enterprise with ≥ 8vCPU/32GB SKUs — analytics workstations, developer profiles, heavy VDI — can activate AI features with a single Intune toggle. No additional budget, no migration. This is the fastest POC of 2026.
⚠️ Watch out for 1. SKU sizing: 2vCPU/4GB or 4vCPU/8GB SKUs are not eligible. Verify your Windows 365 catalog before communicating availability to business stakeholders.
2. Azure region: Confirm Cloud PCs are provisioned in a supported region. Germany West Central is now available — great news for GDPR compliance for German operations.
3. Diagnostic data: Optional diagnostic data must be enabled (required for semantic indexing). Document in your DPIA if subject to GDPR.
4. Recall absent: The session "memory" feature is not available on Cloud PC — local NPU inference remains required for this workload.

These points apply to human Cloud PCs. But the convergence with Windows 365 for Agents introduces an additional dimension to plan for today.

09

Windows 365 for Agents: the agentic identity trap in Intune

Windows 365 for Agents allows CUAs (Computer Use Agents) built with Copilot Studio to run on secure, Entra-joined, Intune-enrolled Cloud PCs. The goal: autonomous AI agents that can open apps, process data, and automate workflows — without dedicated infrastructure.

But when you mix human Cloud PCs and agent Cloud PCs in the same tenant, an implementation subtlety can break your Intune policies entirely.

The 3 Entra objects created per Copilot Studio agent

Entra ObjectTypeRoleVisible in Intune?
Agent blueprint App Registration Agent template — defines Graph permissions, scopes, auth config No
Agentic app instance Service Principal Runtime identity for authentication — federated Teams credentials ⚠ Yes — as SP
Agentic user User (idtyp=user) Org-visible identity — can hold mailbox, OneDrive, M365 license Partial
⚠️ The concrete problem When Intune tries to target an agent, it encounters the agentic app instance — a Service Principal. But Intune drives its provisioning policies through user or device groups, not Service Principals. Targeting breaks if group membership is managed directly from Intune rather than from Entra.

The recommendation: manage in Entra, target from Intune

Recommended management architecture
# Recommended flow ─────────────────────────────────────────────

Copilot Studio  →  creates  →  Agentic User (idtyp=user)
                                ↓
                      Entra ID  →  group  →  "All Agentic Users"
                                or dedicated security group
                                ↓
                      Intune  →  targets group  →  W365 for Agents policies

# AVOID ────────────────────────────────────────────────────────
# Managing group membership directly from Intune
# → Intune sees the Service Principal, not the Agentic User
# → Cloud PC provisioning policies don't apply correctly

# Validation: agentic user token must have idtyp=user
# No traditional credentials (password, passkey, MFA factors)
# MFA-exempt — plan your Conditional Access policies accordingly
Agentic User — key properties
  • ✓Token with idtyp=user — behaves like a user object
  • ✓Can be added to "All Agentic Users" group
  • ✓Assignable to M365 E5, Teams, Copilot licenses
  • ✓Visible in org chart and People Cards
  • ⚠No traditional credentials — MFA exempt by design
  • ⚠Immutably bound to its parent agentic app instance
Intune — current state (preview)
  • ✓Agent Cloud PCs visible: Devices → Windows 365 (partner filter)
  • ✓Entra-joined and Intune-enrolled like human Cloud PCs
  • ⚠Agentic identities displayed as Service Principals
  • ⚠Group membership must be managed from Entra, not Intune
  • ⚠No direct policy assignment via agentic identity in Intune
✅ Operational best practice Create dedicated Entra security groups per agent type (e.g. GRP-W365-Agents-CopilotStudio, GRP-W365-Agents-ProjectOpal) and populate them with agentic users (not service principals). Target these groups from Intune to apply Windows 365 for Agents policies. This human/agent separation is critical as soon as your tenant hosts both types of Cloud PCs simultaneously.
