Le problème actuel : la fusion silencieuse des permissions

The Current Problem: Silent Permission Merging

Le modèle RBAC Intune repose sur trois piliers : le rôle (ce que l'admin peut faire), le scope group (sur quels objets il peut agir) et le scope tag (ce qu'il peut voir). En théorie, c'est un modèle de moindre privilège robuste. En pratique, il existe un comportement non documenté qui crée une dérive systématique des permissions.

Intune's RBAC model rests on three pillars: the role (what the admin can do), the scope group (which objects they can act on), and the scope tag (what they can see). In theory, it's a solid least-privilege model. In practice, an undocumented behavior creates systematic permission drift.

⚠️ Comportement actuel non documenté
Quand un admin est membre de plusieurs role assignments portant sur la même ressource mais avec des scope tags différents, Intune fusionne les permissions de manière additive. Un admin qui a le rôle "Policy Manager" sur le scope tag EMEA et "Help Desk Operator" sur le scope tag APAC peut involontairement se retrouver avec des droits d'écriture sur les politiques APAC — ce qui n'était pas l'intention.
⚠️ Current Undocumented Behavior
When an admin belongs to multiple role assignments covering the same resource but with different scope tags, Intune merges permissions additively. An admin with "Policy Manager" on the EMEA scope tag and "Help Desk Operator" on the APAC scope tag may unintentionally end up with write access to APAC policies — which was never the intent.

Le découplage des scope tags — La migration à préparer

Scope Tag Decoupling — The Migration to Prepare For

Microsoft a annoncé une action one-shot de découplage dans la page "In Development" d'Intune. Le principe : une fois activée, les permissions ne seront plus fusionnées entre role assignments — elles seront strictement appliquées par couple rôle + scope tag.

Microsoft has announced a one-shot decoupling action in Intune's "In Development" page. The principle: once activated, permissions will no longer be merged across role assignments — they will be strictly enforced per role + scope tag pair.

# Audit des role assignments croisés — pré-découplage
Connect-MgGraph -Scopes "DeviceManagementRBAC.Read.All"

$assignments = Get-MgDeviceManagementRoleAssignment -All |
    Select-Object DisplayName, RoleDefinitionId, ScopeMembers, ScopeTags

# Identifier les admins avec plusieurs assignments
$memberMap = @{}
foreach ($a in $assignments) {
    foreach ($member in $a.ScopeMembers) {
        if (-not $memberMap.ContainsKey($member)) {
            $memberMap[$member] = [System.Collections.Generic.List[object]]::new()
        }
        $memberMap[$member].Add($a)
    }
}

# Afficher les admins avec rôles multiples (risque de permission merge)
$memberMap.GetEnumerator() |
    Where-Object { $_.Value.Count -gt 1 } |
    ForEach-Object {
        [PSCustomObject]@{
            AdminId         = $_.Key
            AssignmentCount = $_.Value.Count
            Roles           = ($_.Value.DisplayName -join ", ")
            ScopeTags       = ($_.Value.ScopeTags -join ", ")
        }
    } | Export-Csv "RBAC_CrossAssignment_Audit.csv" -NoTypeInformation

Multi-Admin Approval étendu — Le principe des 4 yeux pour le RBAC

Extended Multi-Admin Approval — Four-Eyes Principle for RBAC

Depuis la mise à jour de février 2026, le mécanisme Multi-Admin Approval (MAA) couvre désormais les changements sur les rôles eux-mêmes. Toute modification de role definition, de member assignment ou de scope tag sur un rôle existant nécessite une approbation secondaire.

Since the February 2026 update, the Multi-Admin Approval (MAA) mechanism now covers changes to roles themselves. Any modification to a role definition, member assignment, or scope tag on an existing role requires secondary approval.

Ce mécanisme est le dernier verrou de la chaîne. Même si un attaquant accède à la console Intune avec des privilèges complets, il ne peut pas élever ses permissions, créer un nouveau rôle admin, ou modifier un rôle existant sans qu'un second administrateur valide l'action.

This mechanism is the last gate in the chain. Even if an attacker reaches the Intune console with full privileges, they cannot elevate permissions, create a new admin role, or modify an existing role without a second administrator approving the action.

🔔 Absence de notifications natives
Intune ne notifie pas les approbateurs des nouvelles demandes en attente. Il est impératif de construire un workflow de notification : canal Teams dédié, boîte partagée, ou Logic App via Graph API (GET /deviceManagement/privilegedAccess/intune/roleAssignmentRequests?$filter=status eq 'Pending').
🔔 No Native Notifications
Intune does not notify approvers of pending requests. It is essential to build a notification workflow: a dedicated Teams channel, a shared mailbox, or a Logic App via Graph API (GET /deviceManagement/privilegedAccess/intune/roleAssignmentRequests?$filter=status eq 'Pending').

PIM pour les rôles Intune — La fin des accès permanents

PIM for Intune Roles — The End of Standing Access

Microsoft recommande désormais explicitement de ne plus utiliser le rôle Intune Administrator d'Entra ID pour les opérations courantes. Ce rôle accorde des permissions globales en lecture/écriture sur tout Intune et ne peut pas être restreint par les scope tags natifs. La bonne pratique : des rôles Intune RBAC custom scopés, activés via PIM en just-in-time.

Microsoft now explicitly recommends against using the Intune Administrator Entra ID role for daily operations. This role grants global read/write permissions across all of Intune and cannot be constrained by native scope tags. Best practice: custom-scoped Intune RBAC roles, activated via PIM as just-in-time.

📌 PIM Method 1 vs Method 2
Deux approches sont supportées : (1) PIM sur le rôle Intune Administrator Entra (élévation en ~10 secondes, mais permissions globales) ; (2) PIM for Groups avec un Intune RBAC role assignment scopé (élévation plus longue ~2 min, mais respect strict du least privilege). Pour les opérations sensibles, la méthode 2 est recommandée.
