01 Attack anatomy — pure Living-off-the-Land

🚨 This is not an Intune vulnerability The attack exploits no CVE, no 0-day, no software vulnerability. The attackers used the organization's own legitimate tools against itself — with valid administrator permissions, on a perfectly normal Microsoft 365 tenant. This is the definition of Living-off-the-Land.
Step 1 — Entry vector
AiTM Phishing — session token theft post-MFA
The vector is not an exploit — it is sophisticated phishing of the Adversary-in-the-Middle (AiTM). A transparent proxy intercepts the Microsoft authentication session in real time. The victim completes their MFA on the real Microsoft page. The attacker captures the session token issued after success — not the credentials, the post-auth token.

Key takeaway: standard MFA (SMS, OTP, Authenticator push) does not protect against AiTM. The attacker bypasses MFA without breaking it — they intercept after the fact.
Step 2 — Persistence
Creation of a new Global Administrator account
With the token of a compromised admin account, the attackers create a new Global Administrator account under their control. Persistence is guaranteed even if the initial account is detected and disabled. Duration of this phase: a few minutes.
Step 3 — Silent exfiltration
50 TB via Microsoft APIs — no alarms triggered
Over several hours — or possibly several days according to sources — 50 TB of data are silently exfiltrated via Microsoft APIs (Graph API, SharePoint, Exchange). No alarms. All of it is legitimate traffic signed by a valid admin account.
Step 4 — Destruction
Bulk Wipe via Intune — 80,000 to 200,000 devices
Via the Intune console, the native Remote Wipe command is executed against the entire enrolled fleet. Laptops, corporate smartphones, and personal BYOD devices are factory-reset — personal photos, eSIMs, and personal banking authentication apps included.

Intune natively supports bulk actions on 100 devices per operation, with no rate limiting, no secondary approval by default. Nothing technically prevents a loop from covering 200,000 machines.

02 Why Intune is a kill switch by design

Microsoft Intune is designed to be authoritative by nature: when Intune sends a command to an enrolled device, the device complies immediately without additional verification. That is exactly what makes it an effective management tool — and a devastating lever when compromised.

Native Intune action Effet Default approval Rate limiting
Wipe (Remote) Full factory reset, all data erased None None
Retire Corporate data removal + unenrollment None None
Delete ManagedDevice Object removal from Intune None None
Bulk actions 100 devices per operation, in a loop None None
⚠️ What Microsoft has changed — and what remains to do Since October 2024: MFA mandatory for all connections to the Intune Admin Center portal. Since October 2025: extended to Azure CLI, PowerShell, mobile apps, IaC tools, and REST API endpoints. 2026: Multi-Admin Approval extended to Settings Catalog and Device Compliance Policies. Standard MFA still does not protect against AiTM.

03 Action plan — from theory to implementation

🔐 Phishing-resistant MFA — PRIORITY 1

~€50/key1 weekFIDO2 / WHfB

Only FIDO2 (YubiKey) and Windows Hello for Business protect against AiTM. Configure an Authentication Strength in Conditional Access that only accepts these methods for Intune Administrator and Global Administrator roles.

✅ Multi-Admin Approval — PRIORITY 1

Free10 minutesDirect mitigation

This native Intune feature requires a second admin to approve any wipe/retire action before execution. It is the most direct mitigation against the Stryker pattern. A secondary approval would have blocked the attack.

⏱️ PIM — No more permanent admin sessions

Entra ID P21 dayJust-in-time

None compte ne devrait avoir Intune Administrator ou Global Administrator en permanence. Avec PIM : élévation just-in-time, durée bornée (1h/4h), approval workflow, audit trail. Un compte compromis hors session PIM active has no power.

🏷️ Scope Tags — Limiting the blast radius

Free1–2 weeksLimited perimeter

Intune Scope Tags restrict the reach of a role to a subset of the fleet. An admin compromised on the "EMEA-Mobile" scope cannot wipe "NA-Workstations" devices.

☁️ Cloud-only admin accounts without Exchange

Free1 dayReduced surface

Admin accounts must never hold an Exchange/M365 license. No mailbox = no AiTM phishing surface. They should exist only in Entra ID, with no access to business applications.

🔒 Conditional Access — Compliant devices only

Entra ID P11 dayDevice trust

Condition: Role = Intune Admin / Global Admin. Requirement: Compliant device + Named Location + Authentication Strength FIDO2/WHfB. Triple verification before any admin access.

04 Microsoft Sentinel — detect and block in real time

💡 Prerequisites Microsoft Intune connector enabled in Sentinel (table IntuneAuditLogs) · Microsoft Entra ID connector enabled (AuditLogs, SigninLogs) · AuditLogs and SigninLogs from Entra ID ingest for free — only IntuneAuditLogs and MicrosoftGraphActivityLogs are billed (~$5/GB).

🔴 Rule 1 — Bulk wipe detection (volume threshold)

Triggers an alert as soon as an admin executes more than 5 destructive actions in 15 minutes. A threshold more than sufficient to distinguish a legitimate operation from an attack.

KQL — IntuneAuditLogs · Scheduled Analytics Rule · Frequency 5min · Severity High 
// RULE 1: Bulk Wipe Detection
IntuneAuditLogs
| where TimeGenerated > ago(15m)
| where OperationName has_any ("wipe ManagedDevice", 
                               "retire ManagedDevice", 
                               "Delete ManagedDevice",
                               "cleanWindowsDevice ManagedDevice")
| extend Props        = todynamic(Properties)
| extend ActorUPN     = tostring(Props.Actor.UPN)
| extend DeviceName   = tostring(Props.TargetDisplayNames[0])
| extend DeviceId     = tostring(Props.TargetObjectIds[0])
| summarize 
    ActionCount  = count(),
    FirstAction  = min(TimeGenerated),
    LastAction   = max(TimeGenerated),
    DeviceList   = make_set(DeviceName, 100),
    Operations   = make_set(OperationName)
  by ActorUPN, bin(TimeGenerated, 15m)
| where ActionCount > 5
| extend AlertSeverity = case(
    ActionCount > 50,  "Critical",
    ActionCount > 20,  "High",
    ActionCount > 5,   "Medium", "Low")
| project TimeGenerated, ActorUPN, ActionCount, AlertSeverity, 
          FirstAction, LastAction, DeviceList, Operations
| sort by ActionCount desc

🟠 Rule 2 — New Global Admin account created (exact Stryker pattern)

This is exactly the persistence move documented in the attack. NRT (Near Real-Time) rule — triggers in seconds.

KQL — AuditLogs · NRT Rule · Free · Severity High 
// RULE 2: New Global Admin Account Created
AuditLogs
| where TimeGenerated > ago(1h)
| where OperationName in ("Add member to role", "Add eligible member to role")
| extend TargetRoleName = tostring(TargetResources[0].displayName)
| where TargetRoleName in ("Global Administrator", 
                           "Intune Administrator",
                           "Cloud Device Administrator",
                           "Privileged Role Administrator",
                           "Privileged Authentication Administrator")
| extend InitiatorUPN  = tostring(parse_json(tostring(InitiatedBy.user)).userPrincipalName)
| extend InitiatorIP   = tostring(parse_json(tostring(InitiatedBy.user)).ipAddress)
| extend TargetUPN     = tostring(TargetResources[1].userPrincipalName)
| extend AssignmentType = iif(OperationName has "eligible", "PIM-Eligible", "Permanent")
| project TimeGenerated, InitiatorUPN, InitiatorIP, 
          TargetRoleName, TargetUPN, AssignmentType, CorrelationId

🟡 Rule 3 — Admin sign-in from new country / risky IP

KQL — SigninLogs · 15min · Severity Medium 
// RULE 3: Admin Sign-in Anomaly — New Country
let AdminRoles = dynamic(["Global Administrator", "Intune Administrator", 
                          "Cloud Device Administrator"]);
let KnownCountries = (
    SigninLogs
    | where TimeGenerated between (ago(90d) .. ago(1d))
    | where UserType != "Guest"
    | mv-expand todynamic(AppRoleAssignments)
    | where tostring(AppRoleAssignments) has_any (AdminRoles)
    | summarize KnownLocations = make_set(Location) by UserPrincipalName
);
SigninLogs
| where TimeGenerated > ago(1d)
| where ResultType == 0
| where UserType != "Guest"
| mv-expand todynamic(AppRoleAssignments)
| where tostring(AppRoleAssignments) has_any (AdminRoles)
| join kind=leftouter KnownCountries on UserPrincipalName
| where Location !in (KnownLocations)
| extend RiskLevel = tostring(RiskLevelDuringSignIn)
| project TimeGenerated, UserPrincipalName, Location, 
          IPAddress, RiskLevel, AppDisplayName, 
          AuthenticationRequirement, DeviceDetail
| where RiskLevel in ("high", "medium") or isempty(RiskLevel)

🔵 Rule 4 — Graph API spike (pre-wipe exfiltration)

The exfiltration of 50 TB before the wipe leaves traces. An API call spike from a single account in a short window is a precursor to the attack.

KQL — MicrosoftGraphActivityLogs · Connecteur requis · 1h 
// RULE 4: Graph API Spike — Pre-Wipe Exfiltration
MicrosoftGraphActivityLogs
| where TimeGenerated > ago(1h)
| where ResponseStatusCode == 200
| where RequestUri has_any ("/devices", "/managedDevices", 
                            "/users", "/groups", "/directoryObjects")
| summarize 
    CallCount        = count(),
    UniqueEndpoints  = dcount(RequestUri),
    BytesOut         = sum(ResponseSizeBytes)
  by UserId, bin(TimeGenerated, 10m)
| where CallCount > 500 or BytesOut > 104857600  // > 100 MB en 10 min
| project TimeGenerated, UserId, CallCount, UniqueEndpoints, BytesOut
| sort by CallCount desc

05 SOAR Playbook — from alert to account disabled in < 60 seconds

The following Logic App triggers on Rules 1 and 2 to automate the response: actor account disabled, token revocation, PIM role removal, and Teams SOC notification.

🤖 Required Managed Identity permissions Graph API Application : User.ReadWrite.All · Directory.ReadWrite.All · RoleManagement.ReadWrite.Directory
Microsoft Sentinel : Microsoft Sentinel Responder
Logic App — Key SOAR Playbook actions 
// Action 1: Disable the actor account
{
  "method": "PATCH",
  "uri": "https://graph.microsoft.com/v1.0/users/@{triggerBody()?['ActorUPN']}",
  "body": { "accountEnabled": false }
}

// Action 2: Revoke ALL active refresh tokens
{
  "method": "POST",
  "uri": "https://graph.microsoft.com/v1.0/users/@{triggerBody()?['ActorUPN']}/revokeSignInSessions"
}

// Action 3: List and revoke active PIM roles
// GET /roleAssignments?filter=principalId eq {userId}
// DELETE /roleAssignmentScheduleRequests/{id}

// Action 4: Teams SOC notification
{
  "text": "🚨 ALERTE WIPE MASSIF - Compte désactivé automatiquement\n
           Acteur: @{triggerBody()?['ActorUPN']}\n
           Devices: @{triggerBody()?['ActionCount']}\n
           Heure: @{utcNow()}\n
           ➡️ Incident Sentinel: @{triggerBody()?['IncidentUrl']}"
}
⚠️ Operational recommendation Do not set the playbook to full-auto on Rule 1 if your environment includes legitimate bulk-wipe procedures (hardware refresh, decommissioning). Configure a dynamic threshold based on 90-day operational history or require SOC validation within 5 minutes. Rule 2 (new GA account creation) can be set to full-auto without operational risk.

08 What this means for CISOs and IT leaders

🚨 The real question is not "could this happen to us?" It is "how long would it take us to respond?" Without Sentinel configured and without Multi-Admin Approval enabled, the answer is probably: after everything is already wiped.

The Stryker attack is not a technological curiosity. It is a signal: endpoint management tools have become a critical attack surface, on par with VPNs and Active Directory. CISA issued an urgent alert on March 18, 2026, stating they were aware of malicious activity targeting endpoint management systems of US organizations beyond Stryker.

The tools exist. They are often already in your licenses. The gap is in the configuration.

Multi-Admin Approval for Wipe/Retire: free, 10 minutes, direct mitigation. It is the first action to take today.
