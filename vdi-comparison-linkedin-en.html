Choosing a VDI platform for thousands of users is rarely a purely technical decision. It is a multi-year operational commitment with direct implications on IT team productivity, service quality, and the capacity to evolve without rebuilding everything. Sometimes, it is also a financial one — and that changes everything.

01 Why AWS WorkSpaces — the decisive factor nobody mentions

💰 The real reason: a multi-million AWS financial commitment The selection of AWS WorkSpaces as the target platform was not driven solely by technical merit. The organization had a significant existing financial commitment with AWS — exiting the contract before its end date would have triggered penalties running into several million euros. This commercial constraint made WorkSpaces the only economically rational choice at the time of decision, regardless of the technical trade-offs documented in this article.

This context is essential to understand what follows. The teams did not choose WorkSpaces blind — they chose it knowingly, with a clear view of its limitations, and invested heavily in custom tooling to compensate for its structural gaps. The result is a pragmatic, industrialized architecture built on top of a constrained platform choice.

This is a reality that vendor comparisons never surface: the best VDI platform on paper is not always the one you can actually deploy. Financial lock-in, existing contracts, and organizational momentum are legitimate architecture constraints — and they deserve to be documented as such.

02 AWS WorkSpaces at 1,600 branches — the blind spots multiply

SAML MFA friction at scale

Authentication relies on two distinct layers: Active Directory on-premises for WorkSpace domain join (Hybrid Join) and network authentication, and Entra ID as the SAML IdP for MFA on the WorkSpaces client. The AWS WorkSpaces client presents the Entra ID SAML portal — once the assertion is validated, the session opens. On a shared workstation in a branch where agents take turns, this full SAML cycle repeats at every session. Across 1,600 sites, SAML assertion failures (IdP token expiry, redirect latency, IAM Identity Center timeouts) generate a measurable helpdesk load.

💡 Conditional Access — applies to M365 services from within the VDI, not to the device The Conditional Access policies target M365 applications (Exchange Online, SharePoint, Teams) accessed from within the WorkSpace — not the local thin client device. The WorkSpace itself cannot be targeted by Intune device compliance CA (no MDM enrollment). CA must be configured to accept Hybrid Joined devices without requiring an Intune compliance signal — otherwise Exchange Online access from WorkSpaces is blocked the moment strict CA is enforced.

Agency segregation: the App Registration anti-pattern

WorkSpaces Personal has no native fine-grained isolation by functional perimeter. The standard workaround: multiply Entra ID App Registrations — one per agency group or functional scope. Across 1,600 branches, even with consolidation by region or business profile, this quickly reaches 50+ App Registrations to maintain: independent secret/certificate rotation cycles, no consolidated view of effective access rights per user, and a distinct audit perimeter per App Reg during compliance reviews.

⚠️ On AVD AVD resolves this by design: Host Pools are assigned to Entra ID groups, Conditional Access applies uniformly across all 1,600 branches from a single policy. Zero additional App Registrations. Compliance audits produce one Entra ID report — not fifty.

FabulaTech × 1,600 agent deployments

AWS WorkSpaces lacks a mature USB/serial device redirection engine comparable to Citrix HDX. FabulaTech for Remote Desktop fills this gap — supporting webcams, local printers, scanners, badge readers, and generic USB peripherals. At 1,600 branches, this introduces: agent maintenance in every golden image update cycle, plug-in maintenance across heterogeneous branch terminals, incompatibility with the AWS WorkSpaces Web client, and a three-tier troubleshooting chain (WS agent + client plug-in + local driver) across 1,600 sites.

03 Dual identity — the W11 thin client on a provider tenant

One of the most architecturally distinctive aspects of this deployment: the Windows 11 thin clients that replaced Citrix endpoints are managed by Intune on a service provider's tenant — not the organization's own tenant. This creates a deliberate dual identity model.

What runs where

  • Local W11 thin client: minimal locked-down usage — browser and WorkSpaces client only. No local productivity apps. No M365 apps (Outlook, Teams). Everything runs inside the VDI. The device acts as a pure display terminal.
  • WorkSpace (VDI): all business applications, Outlook, Teams, intranet, business network flows. The WorkSpace is the actual working environment — the W11 merely carries the display protocol stream.
  • Network flows: the W11 thin client carries only PCoIP/WSP display protocol traffic toward AWS. All application and business network flows originate from the VDI side — toward internet or internal AWS network.

Security stack on the thin client

  • Zscaler ZPA + ZIA deployed on both the W11 thin client and the WorkSpace VDI — two separate Zscaler enforcement points
  • Nexthink for user experience monitoring on the thin client (deployment on VDI is under active debate — sizing constraints at 8 GB / 2 vCPU make it a significant cost discussion)
  • EDR covering both thin client and WorkSpace — full endpoint protection on both sides of the display protocol
💡 Update pipelines — completely separate by design W11 thin clients: Intune + Windows Autopatch (provider tenant) — patches delivered via Microsoft cloud, no dependency on the organization's infrastructure. WorkSpaces VDI: SCCM with Distribution Points hosted in AWS (internal AWS network) — updates delivered entirely within AWS, no WAN dependency. Two completely independent pipelines matching the dual identity architecture.

06 Teams offloading — the transparency myth

✅ UPDATE — Teams offloading on WorkSpaces: now Generally Available (Feb 19, 2026) Microsoft announced GA of Teams VDI optimization for Amazon WorkSpaces on February 19, 2026 — after a public preview that launched in September 2025. Our organization participated in the TAP (Technology Adoption Program) that helped shape this release. This is a fundamental architectural shift: media processing is now offloaded from the VM to the endpoint device entirely.

Why "efficiency is still a debate" — honest field caveats

The architecture is sound and the GA announcement is a real milestone. But at 8,000 users across 1,600 branches on public internet (home broadband boxes), several operational questions remain open from our TAP experience:

  • Slimcore MSIX CDN download on first launch: the package is pulled from Microsoft's public CDN to the endpoint at first use. On Zscaler ZIA-managed thin clients, the CDN endpoint (*.cdn.teams.microsoft.com) must be in the ZIA bypass or allowlist — SSL inspection will break the download silently. With 1,600 branches potentially hitting this simultaneously on rollout day, it's a traffic event to plan for.
  • 8 GB / 2 vCPU WorkSpace sizing: offloading removes media CPU load from the VM — which is good. But if the WorkSpace was already memory-constrained, the Teams client still runs inside the VM for signaling, consuming RAM. No impact on the offloading itself, but worth monitoring with any Nexthink-equivalent telemetry.
  • Thin client hardware floor: Slimcore runs on the endpoint. On older or low-spec W11 thin client hardware, the local decode/encode can saturate the endpoint CPU — the opposite problem from before. Nexthink on the thin client becomes critical to detect this regression.
  • Version alignment: the VDI Bridge, MSTeamsPlugin.dll, and Slimcore MSIX must be version-aligned. SCCM manages the Teams client in the WorkSpace; the WorkSpaces client on W11 is managed by the provider tenant via Intune/Autopatch. Two separate update pipelines — version drift is a real risk.
⚠️ Legacy WebRTC deprecation — AVD and Citrix are also affected The Slimcore/VDI2 architecture is Microsoft's strategic direction for ALL VDI platforms — not just WorkSpaces. AVD and Citrix are currently migrating from the legacy WebRTC-based optimization to VDI2. The legacy WebRTC model introduced version-dependency on external components and infrastructure alignment issues that Microsoft is retiring. Organizations on AVD or Citrix should plan for this transition — the new model aligns Teams VDI with the native client architecture for faster innovation and better reliability.
💡 Monitoring VDI2 offloading status The isOptimized field in Teams diagnostics logs confirms whether VDI2 offloading is active. Monitor via Teams Admin Center → Call Quality Dashboard filtered by branch subnet. With 1,600 branches, any silent fallback to non-optimized mode (VM-side media) will appear as a CPU spike on the WorkSpace fleet — detectable in CloudWatch or SCCM hardware inventory deltas.

07 Profile migration — Citrix CPM roaming profiles

The source environment uses Citrix Profile Management (CPM) with roaming profiles stored on a file server. There are no VHDx containers to mount or dismount — profiles are a plain directory tree on an SMB share. This makes the extraction pipeline significantly cleaner than an FSLogix-based source.

✅ Key advantage: cold extraction, no live session required CPM profiles are stored at \\file-server\profiles\%username%\UPM_Profile\ — a standard file system tree including AppData\Roaming, AppData\Local, and NTUSER.DAT. The collection script runs entirely at rest, without requiring a connected session, by accessing the share directly from a migration server. Citrix sessions are disconnected before the script runs, ensuring PSTs are not locked by Outlook.

Collection script — cold extraction from CPM share

# Cold collection from CPM file server share
$cpmRoot = "\\file-srv\profiles\$username\UPM_Profile"
$staging = "\\mig-srv\staging\$username"

# Outlook signatures (AppData\Roaming — always in CPM)
Copy-Item "$cpmRoot\AppData\Roaming\Microsoft\Signatures" "$staging\Signatures" -Recurse -Force

# Chrome data (AppData\Local — available if CPM policy includes it)
Copy-Item "$cpmRoot\AppData\Local\Google\Chrome\User Data\Default\Bookmarks" "$staging\Chrome\" -Force -ErrorAction SilentlyContinue

# Registry — load NTUSER.DAT hive cold (no live session needed)
reg load "HKLM\TempHive_$username" "$cpmRoot\NTUSER.DAT"
reg export "HKLM\TempHive_$username\Software\Microsoft\Office\16.0\Outlook\Profiles" "$staging\outlook_profiles.reg" /y
reg export "HKLM\TempHive_$username\Software\Microsoft\Office" "$staging\office_settings.reg" /y
reg unload "HKLM\TempHive_$username"

OneDrive Known Folder Move — all folders, zero in FSLogix

The target architecture moves all Known Folders to OneDrive — not just the classic three. Desktop, Documents, Downloads, Videos, Pictures, Music: everything is redirected to OneDrive for Business. Nothing is stored in FSLogix — the Profile Container is reduced to the strict minimum of application AppData Roaming.

⚠️ KFM deployment — first-logon script order matters OneDrive must be started and authenticated before KFM is triggered on large folders. A first-logon startup script (or GPO) must enforce this sequence: (1) verify OneDrive is running and signed in, (2) activate KFM silently via registry, (3) trigger Desktop and Documents first (small, fast), (4) trigger Downloads, Videos, Pictures in background — these can be multi-GB and must not block the logon. Deploying KFM before OneDrive is ready results in empty folders — a perceived data loss for the user.

CIS-hardened VDI — GPO generation via XML parser

WorkSpaces are hardened with a custom CIS profile derived from official CIS benchmarks. Rather than manually maintaining GPO templates, a PowerShell XML parser extracts all recommendations directly from the CIS SCAP/XML benchmark files and injects them into GPOs programmatically:

  • GPOs organized by product scope: Windows OS, Office 2016, Edge, Chrome — one GPO per product for granular control and rollback capability
  • Computer Configuration and User Configuration both covered — with a loopback policy applied on the VDI OU to enforce User scope settings regardless of the user's home OU
  • Maintainability: when CIS releases an updated benchmark XML, the parser re-runs and generates a delta GPO — no manual ADMX hunting
  • The approach is far more auditable than hand-crafted GPOs — every setting is traceable back to a specific CIS recommendation ID in the source XML

08 Exchange Online migration & PST import — 60 TB pipeline

The Exchange migration covers 8,000 user mailboxes + 2,000 shared mailboxes and 60 TB of PST files stored on the AWS file server (CPM share). Since data is already in AWS, the transfer to Azure Blob for Purview Import is intra-cloud — no public bandwidth constraint, no Drive Shipping required.

Exchange — critical points in VDI context

  • Autodiscover V2: with Hybrid Joined WorkSpaces and Entra ID auto-configuration, Autodiscover V2 works natively. The risk is stale SCP records in AD or a PreferLocalXML registry key still pointing on-premises during coexistence — this generates mass re-prompt events at 8,000 simultaneous sessions
  • Modern Auth (OAuth 2.0): with Hybrid Join and M365 auto-config, OAuth 2.0 is the default. Outlook auto-configures silently from the Entra ID token — no credential prompt if the CA policy is satisfied
  • OST reconstruction: plan a first-sync window per user batch. A 30 GB mailbox on a WorkSpace with OST redirected to D: can take 2–3 hours of initial sync — do not validate migration until Outlook has completed its first full synchronization
  • Shared mailboxes and resource mailboxes must be migrated before the users who hold delegations on them

PST migration pipeline — AWS → Azure Blob → Purview

Step 0 — Pre-condition
Disconnect Citrix sessions — PSTs unlocked
Citrix sessions are explicitly disconnected before the collection script runs. This ensures PSTs are not mounted by Outlook and are not file-locked. Safe copy from the CPM share — no corruption risk. No VHDx to dismount, plain SMB file access.
J-15 — Simultaneous with first delta
PSTs set to read-only + first OneDrive delta sync
At J-15, PSTs are set to read-only at the file share ACL level AND via GPO DisablePST (HKCU\Software\Microsoft\Office\16.0\Outlook\DisablePST = 1). Users can no longer modify or create PSTs. All subsequent delta passes (J-10, J-5, J0) capture a frozen, consistent state.
Data migration
1 full copy + 3 delta syncs
1 full copy (AWS → OneDrive) then delta syncs at J-15, J-10, J-5, and J0 for personal data files. The 15-day window is used to verify and remediate: delegations, data completeness, PST import validation, license checks.
PST staging
AWS file server → Azure Blob (intra-cloud)
PSTs are copied from the CPM share to an Azure Blob Storage container (SAS URL provided by Purview Import) via AzCopy. Since data is already in AWS and the transfer goes to Azure, this is effectively intra-cloud — no public internet bandwidth constraint, no Drive Shipping needed for 60 TB.
Corrupted PSTs
Quarantine → remediation → re-inject
Corrupted PSTs detected during collection are moved to a dedicated quarantine folder on the migration server. After remediation attempt, if successful, a CSV file is uploaded to the Blob for Purview Import. If remediation fails, the PST is flagged in SQL and an alert is sent to the project team.
Purview Import
Each PST → named subfolder in Online Archive
Each PST is deposited in a named subfolder within the user's Online Archive (e.g., Archive\PST_2019_filename). This enables precise per-folder item count comparison between source PST and target Archive.

PST integrity verification — Aspose.Email + per-folder item count

Post-import verification compares item counts per folder between the source PST and the target Online Archive. The comparison is done at the folder level (Inbox, Sent Items, custom folders) — not just a global item count. Attachments are not counted separately due to the absence of EWS access on the Archive side (Graph API Get-MailboxFolderStatistics provides item counts but not attachment details).

# PST parsing via Aspose.Email 2.5.11 DLL
Add-Type -Path ".\Aspose.Email.dll"
$pst = [Aspose.Email.Storage.Pst.PersonalStorage]::FromFile($pstPath)
$folders = $pst.RootFolder.GetSubFolders()
foreach ($folder in $folders) {
  $sourceCount = $folder.ContentCount
  # Compare with Graph API Get-MailboxFolderStatistics result
  $targetFolder = $archiveStats | Where-Object { $_.Name -eq $folder.DisplayName }
  $delta = [math]::Abs($sourceCount - $targetFolder.ItemsInFolder)
  [PSCustomObject]@{ Folder=$folder.DisplayName; Source=$sourceCount; Target=$targetFolder.ItemsInFolder; Delta=$delta }
}

Macro signing — enterprise code signing certificate

Macros discovered in Office files during the PST and profile collection phase are signed on-the-fly using an enterprise code signing certificate. This happens in the pre-migration script — before the files are staged to the Blob. The certificate is an internal PKI code signing cert, applied programmatically via PowerShell. Signed macros pass the Office macro security policy in the target WorkSpace environment without requiring the user to take any action.

Data retention — files older than 1 year

Files older than one year have their modification date set to exactly one year ago before migration. This prevents the organization's data retention policy (maximum 6 years) from triggering immediate deletion on data that is technically older. This date manipulation is applied consistently across both personal file migrations and PST content where technically feasible.

🔷 Labeling — deferred to post-project No Microsoft Purview sensitivity labeling solution is in place yet. Labeling will be applied as a separate post-migration workstream. All migrated data (PSTs, OneDrive files) is stored unlabeled and will need to go through a labeling campaign once the classification framework is defined.

09 OneDrive migration — FastTrack & the cross-cloud pipeline

Personal data (CPM profile files, network drive shares) is being migrated to OneDrive for Business. The transfer from AWS to Azure Blob goes through an intra-cloud path — data is already in AWS, staged to Azure Blob, then ingested by Migration Manager. No public internet bandwidth involved.

Step 1
Collection preparation script
A preparation script filters test and admin profiles, verifies that all users have an Entra ID account and an assigned M365 license (via App Registration Graph API call), and generates the FastTrack and Purview CSV files. Only technically verified users enter the migration pipeline. The SQL database maps which migration server handles which agency — batches are balanced by data volume for predictable processing times.
Step 2
AWS → Azure Blob staging (intra-cloud)
AzCopy transfers data from the CPM file server (AWS) to the Azure Blob Storage container used by Migration Manager. Intra-cloud path — no public bandwidth constraint. Blob storage cost applies during the staging window (~$0.018/GB/month LRS).
Step 3
FastTrack + Migration Manager → OneDrive
FastTrack engineers coordinate Migration Manager ingestion from Blob to OneDrive. FastTrack's value is maximum here: long path remediation, naming conflict resolution, per-user completion reports. FastTrack does not cover the AWS → Blob extraction — that's project-owned.
KFM activation
All Known Folders → OneDrive, nothing in FSLogix
KFM Silent policy activates Desktop, Documents, Downloads, Videos, Pictures, Music. Activated via first-logon startup script on WorkSpaces. OneDrive must be running and authenticated before KFM triggers. FSLogix Profile Container contains only AppData\Roaming applicative data — zero Known Folder data.

Migration Manager log correlation — the OneDrive scheduling challenge

Correlating Migration Manager agent logs with schedules defined in the portal (which are associated with migration CSV files) is non-trivial. The agent logs do not carry the schedule ID explicitly. Best correlation strategies:

  • UPN-based matching: Migration Manager logs trace source path and target OneDrive URL per task — the UPN is extractible and serves as the natural join key to the SQL schedule table
  • CSV filename as fingerprint: backend generates CSV names with a unique token (wave3_agencyB_20250412_a7f2.csv) — agent logs sometimes reference the source file name
  • Timestamp + UPN + volume: triple discriminant for cases where filename correlation fails — effective start time from agent log ± 5 min window around SQL scheduled_at, with data volume as tiebreaker

10 Windows version support & SCCM — structural gaps

AWS WorkSpaces — AMI cycle lag

New Windows versions on WorkSpaces are gated by Amazon releasing a new WorkSpaces AMI. This cycle is structurally behind Microsoft's release cadence. Windows 11 23H2 and 24H2 appeared on WorkSpaces several months after Microsoft GA — forcing production fleets to remain on builds approaching end of support. Feature updates require a WorkSpaces Bundle rebuild and manual VM migration; there is no WUfB integration.

⚠️ Compliance implication In environments subject to DORA, ISO 27001, or SOC2, documenting a Windows build on extended support due to AMI unavailability is an auditable non-conformity. AVD and Windows 365 make new Windows versions available in the Azure Compute Gallery within weeks of Microsoft GA. Citrix gives the admin full control — the image is updated when the admin decides.

SCCM with Distribution Points in AWS

Application deployments and OS patches for WorkSpaces are delivered via SCCM, with Distribution Points hosted within AWS on the same internal network as the WorkSpaces. Updates and software deployments are intra-AWS — no WAN dependency, no public bandwidth consumed. This is an architecturally clean match for a fully AWS-hosted fleet.

💡 Bi-site SCCM considerations With two active AWS sites, SCCM Boundary Groups must be defined per AWS site (subnet-based). Each site needs its own DP with replicated content — a WorkSpace that fails over to the secondary site during DRP should not pull updates from the primary site DP across the inter-VPC link. Content replication between the two site DPs must be part of the DRP runbook.

11 Bi-site active-active DRP & the Registration Code problem

The 8,000 WorkSpaces are distributed across two active AWS sites. Each site serves its assigned population in normal operations. In a DRP scenario, half the VMs fail over to the surviving site. This is technically sound — but it exposes a WorkSpaces-specific constraint that can paralyze a DRP in minutes: the Registration Code.

What is a Registration Code?

Before the SAML authentication flow even begins, the AWS WorkSpaces client requires a Registration Code — a unique identifier pointing to a specific AWS Directory in a specific region. This code is stable under normal operations and users never see it once configured. During a DRP failover, WorkSpaces are reassigned to a different Directory — the Registration Code changes. The client on the agent's terminal still points to the old code. The connection fails silently. The agent calls the helpdesk: "I can't open my desktop."

🚨 DRP without preparation On 4,000 users failing over simultaneously, if each one needs to call the helpdesk for a new Registration Code — at exactly the moment the helpdesk is already under DRP pressure — the operational impact is catastrophic. A technically successful DRP becomes a user-experience disaster.

The solution — AWS Lambda for secure Registration Code distribution

Architecture
API Gateway + Lambda + DynamoDB
An HTTPS endpoint (API Gateway) is exposed publicly. The Lambda receives a request with the user's Entra ID UPN, queries a DynamoDB table mapping each user to their current Registration Code (updated during DRP failover), and returns the code securely.
Authentication
Entra ID OIDC/JWT authorizer
The API Gateway is protected by an Entra ID JWT authorizer. Only authenticated M365 users can call the API. The UPN is extracted from the JWT token — no impersonation possible. A user can only retrieve their own Registration Code.
DRP table update
EventBridge rule → sync Lambda
DRP failover triggers an EventBridge rule that calls a sync Lambda. This Lambda queries the AWS Directory Service for current Registration Codes on active Directories and updates DynamoDB. The table must be up-to-date before users start requesting their codes — test this pipeline in every DRP rehearsal.
User experience
Zero helpdesk calls for code retrieval
Automated notification (Exchange Online email, Teams message, or SMS via SNS) sent to affected users with a link to the self-service portal. User authenticates with M365 account → Registration Code displayed → copied into WorkSpaces client → session resumed. Zero helpdesk calls for this failure mode.
💡 On AVD — no equivalent concept The Windows App (formerly Remote Desktop client) connects to the generic URL rdweb.wvd.microsoft.com. Available Host Pools and Application Groups are resolved dynamically from Entra ID. In a DRP failover to another Host Pool or Azure region, the user simply reconnects — their desktop appears. Zero code to distribute, zero client reconfiguration.

PowerShell orchestration pipeline

Step 1
CPM profile collection → Azure Blob
Mounts CPM share, extracts signatures + NTUSER.DAT registry + Chrome data if available. Uploads to wave Blob container. SAS token retrieved from Key Vault via Managed Identity — never hardcoded. SQL status → CPM_PROFILE: IN_PROGRESS.
Step 2
Profile restore → target WorkSpace
Connects to WorkSpace via AWS Systems Manager Run Command. Restores from Blob: Outlook signatures, registry import (Office settings, Outlook profile), Chrome bookmarks if present. SQL → SUCCESS or FAILED with captured error message.
Step 3
OST redirect + OneDrive KFM activation
Sets ForceOSTPath → D:\Outlook via registry. Activates KFM Silent via OneDrive registry policy. Polls Get-ODStatus with configurable timeout to confirm OneDrive sync is running before proceeding — prevents KFM activation before OneDrive is ready.
Step 4
Exchange Online validation
Graph API call to verify mailbox is on Exchange Online. If still on-prem: EXCHANGE → SKIPPED with re-process flag. License and Entra ID account verified via dedicated App Registration before this step — only technically ready users enter the pipeline.
Error handling
Retry + Teams alert + continue
3 retries per step by default. After exhaustion: FAILED + Log Analytics alert → Teams channel notification to project lead. Pipeline moves to next user — individual failures do not block the wave.

CIS-hardened migration VMs — FastTrack agent hosting

SPMT and Migration Manager agents run on dedicated Azure VMs hardened to CIS Benchmark Level 1 (Windows Server 2022). These VMs handle sensitive personal data (emails, files, PSTs) and hold access to Blob SAS tokens and Exchange credentials.

  • CIS L1: unnecessary services disabled, SMB signing enforced, Defender + ASR rules, full audit logging
  • Dedicated service accounts with least-privilege — no Domain Admin, no access outside migration scope
  • No direct internet access — Azure Firewall with allowlist of required M365 and AWS endpoints
  • Admin access via Azure Bastion only — no exposed RDP port, full session auditability

14 Verdicts & contextual recommendations

AWS WorkSpaces — current deployment
Chosen platform · managed debt
Selected as the target platform due to an existing multi-million AWS financial commitment — exiting the contract early was not economically viable. The technical gaps are real but manageable: custom Lambda for DRP Registration Code distribution, SCCM DPs in AWS for deployment, dedicated print network eliminating VDI contention, and a purpose-built Azure migration backend compensating for the lack of native Intune tooling. The structural limitations (no Teams offloading, AMI lag, no Intune enrollment) are known and monitored.
Citrix DaaS
The mature enterprise standard
Still the most complete solution on advanced features: Universal Print (CUP), Profile Management (CPM), native USB redirection (HDX), session recording, granular DLP. Justified for GPU workloads, complex multi-cloud environments, and organizations with large concurrent user ratios. High TCO and operational complexity are justified at scale. Post-acquisition roadmap (Cloud Software Group) warrants monitoring.
Azure Virtual Desktop
Best overall value
The optimal platform for Microsoft-centric organizations migrating from Citrix. Native Intune, Entra ID SSO without App Registration proliferation, FSLogix included, WUfB, Scaling Plans, Windows Multi-Session for density economics, Teams Media Optimization, Universal Print. The IC3/IME trajectory positions it as the most modern VDI platform at 2026 horizon. Recommended for knowledge worker populations.
Windows 365
Maximum operational simplicity
Ideal for branch agents, frontline workers, and subsidiaries without dedicated IT expertise. Fixed cost, zero infrastructure to manage, Intune as the single control plane, transparent Exchange/OneDrive migration. The "branch agent" profile — fixed location, business applications, 8h/day — maps perfectly to the Cloud PC model. Natural complement to AVD on the same tenant with a unified Intune control plane.
✅ Greenfield recommendation — 8,000 users · 1,600 branches · full Microsoft stack Without the AWS financial constraint: AVD (knowledge workers, multi-application sessions, density needs) + Windows 365 Frontline (branch agents, fixed profile). Exchange Online via Hybrid Configuration Wizard. FastTrack for OneDrive onboarding + full KFM. PST import via Purview — intra-Azure, zero transfer cost. Universal Print for branch printing (lightweight on-premises connector). Single control plane: Microsoft Intune. Single identity: Entra ID with Conditional Access — zero VDI-specific App Registrations.
